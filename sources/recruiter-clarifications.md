# Recruiter clarification supplied by the candidate

The following is an English rendering of the Romanian response provided in the
conversation. It is source context, not a new implementation specification.

The evaluation does not concern the choice of a particular product. It concerns
how the problem is analyzed, decomposed, and solved technically. The exercise
should produce a design and implementation artifact for the technical interview,
where decisions, trade-offs, and reasoning will be explored.

1. Systems may be real, fictional, or a combination. There is no preferred product.
   The choice should enable discussion of architecture, integration, and design.
2. Adobe products or test environments will not be provided. An Adobe API may be
   simulated, but doing so is not required. Product-specific Adobe knowledge is
   not the evaluation target.
3. Real APIs and local simulators/mocks for one or both systems are acceptable.
   Explain the assumptions and choice. Architecture clarity, scenario validation,
   and technical reasoning matter more than actual platform connectivity.
4. A unidirectional flow is sufficient if it solves the problem and documents
   reconciliation, error handling, and conflict-resolution rules. Bidirectional
   synchronization should have a value justification. There is no predetermined
   correct architecture; the evaluation concerns trade-offs and reasoning.

The candidate additionally clarified that the interviewers are not Java-based
and the discussion will emphasize design/architecture. A Stripe test account
already exists. AI orientation should be in agent instructions and development
workflows, with runtime AI only mentioned as a considered backlog extension.
